# ExifFrame project map
- Windows is the only supported operating system. Product, desktop application, documentation and executable use ExifFrame; pyproject.toml retains the legacy distribution name semi-photo-utils.
- `main.py` launches the native Windows photo workspace. For Qt file browsing, template editing, previews, export behavior and lifecycle: `mem:studio/core`.
- `web_server.py`: legacy Flask instance `api`, configuration/template/file APIs, batch orchestration and streamed progress. `templates/index.html`: browser UI and embedded JavaScript.
- `core/`: resource paths, EXIF extraction/editing, cached Jinja rendering and image assets, logging. `processor/`: extensible Pillow pipeline.
- For the 27 editable EXIF fields, watermark-only overrides and protected copy/migration semantics: `mem:metadata`.
- For free footer-field placement/order/separators and visual/advanced-source editing: `mem:footer`.
- Runtime assets live under `config/` (INI, JSON/Jinja templates, fonts, logos); `static/` includes example templates/previews. Runtime template lookup uses `config/templates`, not the example files.
- Source and onedir runs use the application directory. Marked single-file builds read static resources from the PyInstaller bundle, seed editable config/templates/fonts/logos once beside ExifFrame.exe (or under explicit `EXIFFRAME_DATA_DIR`), and use that persistent directory as the working directory. The lock and initialization marker live inside config; existing files and deletions survive later launches. First launch can copy missing files from the old `%LOCALAPPDATA%/ExifFrame/config` without changing its source, resolving old relative input/output paths against the old data directory. Existing neighboring configuration takes precedence. ExifTool prefers the executable's neighboring `exiftool/` directory, then the bundled copy.
- Batch flow: load chosen template -> render separately for each photo with `exif`, `filename`, `file_dir`, `file_path`, `files` -> JSON parse -> pipeline. Output mirrors the input-relative directory; existing output is skipped unless overwrite is enabled.
- Processing progress is a POST response with `text/event-stream`; browser consumes it through streaming fetch. Thread pool runs up to four files concurrently. Preserve event format when changing backend/UI.
- For registry, image buffers and processor extension invariants: `mem:processor/core`.
- For interpreter/dependencies, frontend libraries and Windows packaging: `mem:tech_stack`.
- For environment setup, run/build commands and PowerShell usage: `mem:suggested_commands`.
- For naming, configuration representation and extension style: `mem:conventions`.
- For available validation and completion checks: `mem:task_completion`.
- For memory naming, references and maintenance thresholds: `mem:memory_maintenance`.
