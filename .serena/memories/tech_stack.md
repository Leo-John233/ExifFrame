# Toolchain and runtime dependencies
- Windows is the only supported operating system. Python >=3.13 in `pyproject.toml`; `.python-version` selects 3.13, matching Windows packaging CI.
- Three dependency routes coexist: project dependencies + `uv.lock` for uv, `requirements.txt` for pip development, and pinned `build_support/requirements-windows.txt` for Windows CI. Do not assume lockfile edits affect the release workflow.
- Backend: Flask/Jinja2; image work: Pillow, pillow-heif (registered on processor package import), NumPy; logging: Loguru; project TOML loading uses standard-library tomllib (Python >=3.13). Avoid reintroducing a runtime tomli import: its compiled PyPI wheel can require a hash-named mypyc module omitted from a frozen app even when a different local distribution works.
- `pystray` is declared in project dependencies but absent from requirements.txt; assess which installation path a dependency change must support.
- Legacy browser frontend is one Jinja HTML template with Alpine.js, Tailwind CDN, Ace JSON editor and Toastify loaded from CDNs. No Node package manifest or frontend build pipeline; a fully offline backend does not imply offline UI asset availability.
- EXIF lookup checks the source root or frozen executable directory and, in single-file mode, the embedded resource directory. Both exiftool/exiftool.exe and exiftool/exiftool(-k).exe require adjacent exiftool_files; no PATH lookup. UTF-8 stdin argument streams avoid Windows filename encoding loss; JSON -l aliases preserve original template keys. Pillow fallback applies only when extraction is unavailable.
- Config INI is read and written explicitly as UTF-8; retain this for Chinese template names under Windows' default GBK locale.
- Native UI uses PySide6. `build_support/build_windows.py` and `windows.spec` build an isolated single-file build/ExifFrame.exe by default, embedding configuration defaults, templates, fonts, logos, static assets, project metadata and the complete project exiftool directory. Only NumPy's fixed wheel is downloaded/cached by the local builder; it is directly unpacked into the system temporary directory, not pip-installed. Analysis and staging stay outside the workspace and are cleaned on success/failure; no persistent work cache is retained. Keep build/dist excluded from VS Code watching and Python analysis. build_guard.py limits Windows build child trees to two logical CPUs, below-normal priority, one numerical thread and a memory allowance capped at 4 GiB, with per-stage timeouts. The pinned PyInstaller process uses single-file CArchive compression level 6 to reduce compression work. Onedir emits a fresh output directory with external resources; prior outputs/user data are preserved. The GitHub-hosted workflow separately prepares and caches official ExifTool before calling the same builder; this cloud-only download is explicitly authorized. CI uses Windows 2025/Python 3.13 x64, caches pip/NumPy, runs one startup check and automatically publishes a GitHub Release with the EXE after a successful build. It uses contents:write and step-scoped GH_TOKEN, with no Actions artifact upload. User configuration defaults to config beside the executable. See `mem:suggested_commands`.
- Qt Chinese QM files are bundled under translations; i18n searches QLibraryInfo, frozen _MEIPASS and external translations paths. No new Tkinter or calendar package dependency.
- PyInstaller child-process compatibility bootstrap is in build_support/sitecustomize.py; Conda Pillow decoding DLLs are collected explicitly. Native architecture details: `mem:studio/core`.
